# DeeOverlays — постоянные инструкции проекта

## 1. Проект

Название продукта: **DeeOverlays**

Разработчик и владелец продукта: **DeeNet Studio**

DeeOverlays — платформа для создания, настройки и использования адаптивных стриминговых оверлеев с последующим отображением через OBS Browser Source.

В дальнейшем проект должен поддерживать:

* универсальные стриминговые оверлеи;
* игровые оверлеи;
* различные разрешения и соотношения сторон;
* отдельный Overlay Runtime;
* получение данных в реальном времени;
* игровые интеграции;
* локальный DeeOverlays Agent;
* серверную инфраструктуру;
* пользовательские конфигурации;
* персональные URL оверлеев.

Не реализовывать будущие функции самостоятельно без отдельного задания.

## 7. Архитектура DeeOverlays

Сохранять принцип разделения:

### Editor

Полный интерфейс настройки оверлея.

### Overlay Runtime

Лёгкая веб-сцена, предназначенная для отображения в OBS Browser Source.

Редактор и Runtime могут использовать общие визуальные компоненты и общую модель конфигурации, но Runtime не должен загружать ненужную редакторскую логику.

Не смешивать Editor и Runtime в один монолитный компонент.

## 9. Адаптивность

Адаптивность — обязательное фундаментальное требование DeeOverlays.

Нельзя считать `1920×1080` единственным рабочим разрешением.

Необходимо учитывать:

* 16:9;
* 16:10;
* 4:3;
* 21:9;
* нестандартные размеры Browser Source;
* разные физические разрешения.

Не строить систему на жёстко заданных абсолютных координатах под одно разрешение.

Не использовать один глобальный `transform: scale()` как основную систему адаптации.

Использовать подходящие современные механизмы CSS и относительное позиционирование.

## 16. Производительность

* игрой;
* захватом видео;
* кодированием;
* другими Browser Source.

Не использовать без необходимости:

* огромные box-shadow;

* тяжёлые бесконечные JavaScript-анимации;
* постоянные лишние React-render;
* polling с высокой частотой.

Для простых визуальных анимаций предпочитать:

* CSS transform;
* opacity;
* transition;
* animation.

## 20. Коммиты

Каждый законченный и проверенный этап разработки должен фиксироваться отдельным Git-коммитом.

Коммит создавать только после успешного завершения проверок.

Сообщение коммита должно кратко и понятно описывать выполненную работу.

Предпочтительный формат:

```text
feat: добавить Overlay Runtime для OBS
fix: исправить адаптацию чата на 4:3
refactor: вынести общую конфигурацию оверлея
```

Не объединять несколько крупных независимых этапов в один непонятный коммит.
